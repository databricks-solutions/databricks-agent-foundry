# UI Template Overrides

This directory contains file-level overrides for the upstream
`e2e-chatbot-app-next` template (sparse-cloned from
`databricks/app-templates`). Each file replaces its counterpart in the
cloned template at startup via `_apply_overrides()` in `start_app.py`.

**Upstream repo**: <https://github.com/databricks/app-templates>
**Upstream commit**: see `UPSTREAM_TEMPLATE_SHA` in [`bricks/app/scripts/start_app.py`](../../../../bricks/app/scripts/start_app.py) (canonical source of truth — pinned at clone time via `git checkout`). Currently `861de21f0dcd90572293fd883d51f863dce94e05` (2025-04-16).

## Hard rule: only overlay-bound files live here

`_apply_overrides()` does an unconditional `rglob("*")` over this entire
tree (excluding `MANIFEST.md`) and rsync-copies every file onto the
upstream checkout. That means **every file under `overrides/` either
replaces an upstream file or lands as a sibling next to upstream files**
— there is no "tools-only" or "developer-only" sub-tree.

Concretely, do **not** add to this tree:

- `package.json` / `package-lock.json` / `node_modules/` (a stray
  `server/package.json` will clobber upstream's `@databricks/chatbot-server`
  workspace declaration and break the build — caught the hard way after
  a deploy crashed `dev-fancy-agent-app`). The only `package.json`
  files here are verbatim upstream mirrors under the additive policy below.
- Standalone unit tests (`*.test.ts`, `*.spec.ts`) — they pollute the
  upstream tree and may confuse the build.
- Documentation, READMEs (`MANIFEST.md` is the one allowed exception
  because `_apply_overrides` skips it by name).

Anything that's only useful at *development time* — test harnesses, lint
configs, dev-only `package.json` files — must live somewhere else in
the repo. The TS unit-test harness for files in this tree lives at
[`payloads/agent/ui/tests/ts/`](../tests/ts/) for exactly this reason.

## Fence-dispatch contract

[`client/src/components/elements/response.tsx`](client/src/components/elements/response.tsx) overrides Streamdown's default `code` component with a tiny dispatch table. Each fenced markdown block whose language tag matches a registered key is rendered by the registered `FenceRenderer`. Any other block fence (e.g. ```python) renders through the shared `CodeBlock` — a syntax-highlighted `<pre>` box with a Copy button — and inline code renders as a styled inline `<code>`. (Because this override owns the `code` component and Streamdown's default `pre` is a pass-through, a bare `<code>` fallback would drop the `<pre>` wrapper and collapse a block's line breaks into one run-on line.)

| Language tag | Renders | When emitted |
|---|---|---|
| `echarts-chart` | Interactive ECharts chart | Agent writes the fence directly into its assistant text reply (see system-prompt addendum in the downstream's `payloads/agent/payload.yml` `spec.runtime.system_prompt`). Gated by `spec.ui.charts.enabled`. |
| `mermaid` | Mermaid diagram (code block until the text parses) | The model writes it in an answer or a report. Always on, as in upstream Streamdown. |
| `svg` | SVG shown as an `<img>` + Copy + SVG download (code block until it is a complete SVG document) | The model writes it in an answer or a report, prompted by [`runtime/chat_rendering.py`](../../runtime/chat_rendering.py). Always on. |
| `markdown-report` / `markdown-report:<filename>` | Rendered Markdown report card + Copy + Markdown (`.md`) and HTML downloads | The agent's `_report` tool files it ([`runtime/report_tool.py`](../../runtime/report_tool.py)), or the model writes it with an outer fence of four or more backticks. Gated by `spec.ui.reports.enabled`. |
| `sql-download:<filename>:<base64>` | SQL block + Copy + Download | Currently no default emitter — SQL is rendered inside the Tool panel via the `tool.tsx` override.  Available for downstreams that opt-in via the `tool_output_renderers.py` registry. |
| `table-download:<filename>:<base64>` | Paginated table | Same — Tool panel handles the table; tag still available for opt-in fence emission. |
| `json-download:<filename>:<base64>` | JSON block + Copy + Download | Available for any agent that wants a downloadable JSON block in its reply. |

Feature PRs register handlers at module load via:

```ts
import { registerFenceRenderer } from './response';
registerFenceRenderer('echarts-chart', (children, className) => /* ReactNode | null */);
```

Returning `null` from a handler is treated as "fall through to the default rendering" (the highlighted `CodeBlock` for a block fence) — useful for graceful degradation on parse failure.

## Server-side: chart helpers

Agents emit chart fences explicitly via [`payloads/agent/runtime/chart_helpers.py`](../../runtime/chart_helpers.py):

```python
from payloads.agent.runtime.chart_helpers import render_chart

md_block = render_chart(
    chart_type="bar",
    data=[{"q": "Q1", "rev": 120}, {"q": "Q2", "rev": 150}],
    x="q",
    y=["rev"],
    title="Revenue by Quarter",
)
```

`render_chart` returns a markdown fenced block (` ```echarts-chart `) ready to embed in the agent's response. Validation is eager — unsupported `chart_type`, oversized `data` (cap: 500 rows), `x`/`y` referencing missing fields, or conflicting axis/layout options raise `ValueError` at emit time. The helper must stay in sync with `chart-option.ts` (`CHART_TYPES`, `STACKABLE_TYPES`, `HORIZONTAL_TYPES`, `MAX_SANKEY_NODES`, `layoutErrors`) and `chart-spec.ts` (`MAX_DATA_ROWS`, `MAX_AXIS_NAME_LENGTH`, `MAX_REFERENCE_MARKS`).

### Wide-format-only schema (intentional)

The `ChartSpec` schema is deliberately small: `type`, `data`, `x`, `y`, optional `title` / `palette`, plus optional presentation settings — `xType` (`category` or `time`), `xName`, `yAxis` (`name`, `log`, `min`, `max`), `stacked` (bar/area), `horizontal` (bar), `y2` / `y2Axis` (series on a right-hand axis), `size` (bubble scatter), `target` (sankey flow destination; `x` is the source) and `referenceLines` / `referenceBands` (at most five each, measured against the left axis; `axis: "x"` is the category/time axis whatever the orientation). **There is no `groupBy` / `aggregation`.** Multi-series charts are produced by passing wide-format data: one row per `x` value, one column per series listed in `y`. The agent prompt instructs the model to pivot via SQL (`GROUP BY x_col` + per-series `CASE` / pivot) before emitting the spec — the renderer stays a pure plotting layer with no bucketing logic.

Cross-field rules (for example `horizontal` only on `bar`, no `stacked` on a log axis, no `y2` with `stacked`, numeric values for value-axis reference marks) live in `layoutErrors()` in `chart-option.ts`; the Zod schema applies them through `superRefine`, so a conflicting spec falls back to the code block. When the toolbar switches to a type that does not support an option, the builder drops that option instead of failing. Charts with more than 50 x values get a zoom slider (slider only — an in-chart wheel zoom would hijack chat scrolling).

This trade-off keeps the option builder small, eliminates an entire class of long-format / null-vs-zero edge cases, and pushes data shaping to where the data already is (the SQL warehouse).

## Server-side: tool output renderers

The registry in [`payloads/agent/runtime/tool_output_renderers.py`](../../runtime/tool_output_renderers.py) lets future tool integrations emit extra UI-targeted markdown after a tool returns. Each renderer is keyed by a tool-name regex and may return a markdown string (rendered as an extra `message` text part in the UI stream) or `None` (skip). Renderers are invoked from [`payloads/agent/runtime/stream_utils.py`](../../runtime/stream_utils.py) immediately after the original `tool_call_output_item` is forwarded to the UI; the original tool-result item is **never** modified.

**The registry ships empty.** SQL warehouse results are rendered client-side directly inside the Tool panel by the `tool.tsx` override — emitting the same content as a fenced `message` part too would cause a duplicate table in the chat.

A reference SQL renderer (`render_sql_warehouse_output`) is still exported; downstream apps can opt in by calling `register(re.compile(r"sql_warehouse__execute_sql"), render_sql_warehouse_output)` at agent startup. Add new renderers (Genie, UC functions, etc.) the same way.
