# payloads/agent/deploy/skills/

> **Technical reference** for deployers and developers.

A repo skill is one directory with one `SKILL.md`: YAML frontmatter with
`name` and `description`, then a free Markdown body. The assembler puts the
skills into the agent's system prompt at deploy time. Skills carry
instructions only; the agent's tools come from `mcp_servers/` (and, rarely,
`spec.runtime.tools.definitions` in `payload.yml`).

> **An agent-payload capability.** Skill assembly runs inside the `app` deploy via the payload's provision manifest (`payloads/agent/deploy/skills/step.py` → `payloads/agent/deploy/assembly.py`). The validate/assemble implementation and the `_scaffold/` tree live here; skills are authored under `instances/<app>/payloads/agent/skills/`.

```
instances/<app>/payloads/agent/skills/
  sql-runner/
    SKILL.md              # required
    eval/questions.yml    # recommended
  _assembled/             # generated by the deploy
```

## Contents

| Path | Purpose |
|------|---------|
| `_scaffold/skill/` | Starter skill, written to `skills/my-skill/` by `agent-foundry scaffold skills` |
| `assemble.py` | Compose the skills into the system prompt (and the lazy skill index) |
| `validate.py` | Check the skills against the rules below |
| `common.py` | The typed `RepoSkill` both formats load into, plus shared checks |
| `_legacy.py` | The deprecated format, read for one release |

## Workflow

```bash
uv run agent-foundry scaffold skills --instance my_app          # skills/my-skill/
# rename the directory and the frontmatter name, write the body
uv run agent-foundry brick skills validate --instance my_app
uv run agent-foundry brick skills assemble --instance my_app    # optional: deploy runs it
```

`assemble` writes `instances/my_app/payloads/agent/skills/_assembled/system_prompt.md`.

## `SKILL.md`

```markdown
---
name: sql-runner
description: Runs read-only SQL against Unity Catalog. Use when the user asks for numbers from a table.
---

# SQL runner

How to do the work: steps, examples, output format, edge cases.
```

| Rule | Severity |
|------|----------|
| The directory name is a slug: lowercase letters, digits, single hyphens, at most 64 characters | error |
| Frontmatter `name` equals the directory name | error |
| `description` is non-empty and at most 1024 characters | error |
| The body is non-empty | error |
| The file has at most 500 lines | warning |
| `eval/questions.yml` exists with at least 3 questions | warning |
| A leftover `skill.yml` / `prompt.md` / `tools.yml` next to `SKILL.md` is ignored | warning |

Write the description so the model can pick the skill from it alone: what
the skill does and when to use it. The body has no required headings.

The frontmatter rules are the shared contract in
`agent_foundry/contracts/skills.py`. Unity Catalog skill bundles,
user-authored gateway skills and Lakebase user skills use the same parser
and slug pattern; only their size limits differ.

## Loading

`spec.runtime.tools.skills.loading` picks how skills reach the model:

- **`eager`** (default): the system prompt gets a `## Skills` section with
  `### Skill: <name>`, the description and the body of every skill, sorted
  by directory name.
- **`lazy`**: the system prompt gets only the `## Loadable skills` index
  (one row per skill: id, name, description), the same index user and
  gateway skills use. The model loads a body with `_load_skill`. The deploy
  also writes `_assembled/skill_index.json`, which maps each id to its
  `SKILL.md`. `routing_header` replaces the prose above the rows. With
  `context.prompt_cache.enabled` (the default), lazy is deployed as eager.

## Deprecated format: `skill.yml` / `domain.yml`

Skills written as `skill.yml` + `prompt.md` + `tools.yml`, optionally
grouped under a `domain.yml` directory, are still read for one release,
with a deprecation warning from `validate`. They render exactly like
`SKILL.md` skills:

| Old | Now |
|-----|-----|
| `skill.yml` `name`, `description` | `SKILL.md` frontmatter |
| `prompt.md` | `SKILL.md` body |
| `skill.yml` `triggers` | Put them into the description ("Use when ..."); they are no longer rendered |
| `skill.yml` `phase` | Gone; skills are sorted by directory name |
| `domain.yml` grouping | Gone; skills are flattened, the domain directory is not part of the id |
| `domain_prompt.md` | Move shared context into `spec.runtime.system_prompt`; it is no longer rendered |
| `tools.yml` | An MCP server under `mcp_servers/`, or `spec.runtime.tools.definitions` |

Until the format is removed, legacy `tools.yml` entries still become
`_assembled/skill_tools.json` direct-mode tools. A `genie` or
`vector_search` entry with only `name` gets its `space_id` / `index_name`
from the `genie_spaces/<sub>/space.yml` or
`vector_indexes/<sub>/index_config.yml` whose `tool_name` (default: the
directory name) matches. Entries with only `name` and `description` are
references to MCP server tools and must appear in a `tools.allow` list.

## Tools defined in `payload.yml`

#### `python` function tools

A `python` tool maps to a module-level Python callable by dotted import
path (`callable_path`, e.g. `my_pkg.tools.add_signal`) and is wrapped as a
`FunctionTool` the LLM can call. It runs **in-process**, so a set of such
tools can accumulate state across calls within a single request (on the
run `state` object, below) and hand the assembled result back
**out-of-band** through the `custom_outputs` finalize hook rather than as
prose (see below).

- **Attachment**: unlike the direct-mode Genie / Vector Search tools, a
  `python` tool is attached **regardless of `tools.mcp_only`** -- it is
  first-party in-process code, not a legacy transport the flag gates.
- **Argument schema**: omit `params_json_schema` to have the runtime infer
  a primitives-only schema (`str` / `int` / `float` / `bool`) from the
  callable's signature; provide an explicit schema (e.g. a Pydantic
  model's `model_json_schema()`) for nested / container / typed args.
- **State (opt-in)**: a leading parameter named `state` receives the
  request-scoped `RequestState` -- the same object threaded through the run
  and shared by every `python` tool call -- and is not exposed as an LLM
  argument. (Only the name `state` opts in; a parameter named `ctx` or
  `context` is an ordinary LLM argument.) Accumulate on its opaque `data`
  bag, e.g. `spec = state.data.setdefault("spec", MyReportSpec())`; the
  framework never inspects `data`. `state.request` is the request on the
  `@invoke` / `@stream` path and `None` on the `run`/`repl` paths, so use
  `data.setdefault(...)` rather than assuming `reset` seeded it. `state` is
  the only supported per-request accumulator: module-level state (e.g. a
  `contextvars.ContextVar`) is unsupported, and a tool module that defines
  a module-level `ContextVar` gets a deprecation warning at load.
- **Sync vs async**: sync callables run inline. Because state lives on the
  passed `state` object, state correctness does not depend on inline
  execution -- a callable that may block (SQL, network) can be declared
  `async` freely so it does not stall the event loop.
- **Failures fail soft**: an exception is logged and returned to the model
  as a short error string; a bad `callable_path` is skipped with a warning
  at agent build (never a crash).
- **Import root (enforced)**: the framework adds the active instance dir to
  `sys.path` at startup, so `callable_path` is rooted at `instances/<name>/`
  -- e.g. `mda_tools.spec_tools.add_signal` resolves to
  `instances/<name>/mda_tools/spec_tools.py`, and a vendored
  `instances/<name>/mda_report_spec/` imports as `mda_report_spec`. This
  works identically in the deployed App and in `agent-foundry run`/`repl`.
  Loading is **fail-closed** to that dir: the top-level package is located
  without executing it and must live in the instance dir, the imported
  module's file must too, and so must the callable's defining module (a
  re-export such as `from requests import get` is refused). A path to an
  installed or stdlib module, or an instance package shadowed by an
  installed one of the same name, is rejected and the tool is skipped with
  a warning. The same check applies to the `reset` / `finalize` hooks.
- **Packaging**: vendor the code (and any third-party dependency) under
  `instances/<name>/` -- the only tree the deploy staging ships alongside
  the framework wheel.

#### Out-of-band structured output (`spec.runtime.finalize` / `reset`)

Two optional, generic lifecycle hooks (dotted import paths, same mechanism
as `python` tools) let an instance return a structured object without
stuffing it into the assistant's prose. Each hook may declare a `state`
parameter to receive the request's `RequestState` (the object the `python`
tools accumulated on), plus `request` (and `finalize` also `result`); the
runtime passes only the parameters the callable declares.

- `spec.runtime.reset` -- runs at the start of each request; seed
  `state.data` here before any tool runs.
- `spec.runtime.finalize` -- runs after the run completes; read `state.data`
  back and return a dict, which is merged into
  `ResponsesAgentResponse.custom_outputs` (and emitted as a trailing
  `response.completed` event on the streaming path).

If you don't use `finalize`, the fallback is to call a
`get_report_spec()`-style `python` tool last and read its JSON result from
the response items.

#### Trust model & isolation

`python` tools (and the `reset` / `finalize` hooks) run **in the App process,
as the App's service principal**, with no sandbox. Treat them accordingly:

- **Instance-author primitive.** `type: python` (and the hook paths) is for
  **instance authors**, not a skill-catalog or end-user primitive. A
  `callable_path` is config authored in the instance repo and must resolve
  to code vendored under `instances/<name>/`; this is **enforced at load**
  (see "Import root" above), so a path can never run an installed module.
  It is *not* derived from chat input, from an end user, or from a
  shared/remote skill catalog. The model chooses *when* to call a tool and
  *with which arguments*, but never *which code runs*, so the security
  posture is that of the instance repo you already deploy. Do not wire a
  `callable_path` that is influenced by untrusted input.
- **The callable runs with full App authority** (UC, secrets, warehouse,
  egress). Keep tool functions to **in-memory compute** (build/validate a
  result object, accumulate on `state.data`). **Route I/O (SQL, network,
  catalog access) through an MCP server (or Genie / Vector Search / UC)**,
  which is the transport with the OBO scoping and rails. The instance-dir
  check guarantees only instance-authored code runs; it does **not** stop
  that code from importing a network or SDK client itself. Ambient I/O
  inside instance code is not blocked in-process: keeping it out is part of
  the instance-author contract.
- **Module top-level code executes at import** (agent-build time), before any
  request. Keep tool modules import-clean: no side effects, no work at import.
- **No process isolation / kill switch.** A `python` tool shares the
  interpreter (and, for sync tools, the event-loop task) with the App. A
  native crash, `os._exit`, OOM, or a blocking sync call can therefore affect
  the App; `except`-based fail-soft only covers ordinary exceptions. Mitigate
  by keeping tools fast and in-memory, and by declaring any potentially
  blocking callable `async` (state now lives on `state`, so async is safe) so
  it yields the event loop. If a future use case needs untrusted or heavy
  compute, run it out-of-process (the `extract_worker` subprocess pattern used
  for file parsing) or behind MCP, not as an in-process `python` tool.
- **`reset` / `finalize` are callables by design.** They stay dotted-path
  callables (not a declarative mapping) because real hooks carry logic
  (seeding precedence, persistence, mapping `state.data` to `custom_outputs`)
  that a static mapping can't express. They share the same trust boundary as
  tool `callable_path`s above.

> After upgrading agent-foundry, consumers with a vendored schema copy
> (`.agent-foundry/schemas/tool_manifest.schema.json`) should run
> `agent-foundry sync-schemas` to pick up the new `python` tool type.
